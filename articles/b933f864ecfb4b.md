# はじめに

OxlintとOxfmtはRustで実装された高速なLinter/Formatterです。ESLintやPrettierと比べて実行速度が大幅に向上することが報告されており、導入メリットは大きいです。

一方で、「既存プロジェクトに問題なく移行できるのか」「今まで検出できていたルール違反がそのまま引き継がれるのか」という不安を持つ方も多いかと思います。私もそのうちの一人です。

この記事では、ESLint/Prettierで検出していた違反がOxlint/Oxfmtでも同様に検出されるかを検証します。公式の`migrate`コマンドを使った移行手順と検証結果を、実際のコードと実行出力で確認していきます。


# ESLintとPrettierを確認


今回検証に使用するアプリは TypeScript / TailwindCSS / React / Next.js な構成にしています。

	);

`migrate`実行時にスキップと警告が発生しているので確認します。

### スキップされたルール
スキップされたルールは出力の通り3種類に分類されます。

**Nursery (4件)**
```
4 Nursery (Experimental: react/require-render-return, getter-return, no-undef, and more)
```
NurseryとはOxlintにおける「開発中で将来変更される可能性があるルール」のカテゴリです（公式定義: *Rules under development that may change*）。  
デフォルトではスキップされますが、`--with-nursery`フラグを指定することで有効化できます。

**Not Implemented (1件)**
```
1 Not Implemented (Not yet in oxlint: react/no-deprecated)
```
`react/no-deprecated`はOxlintにまだ実装されていないルールです。現時点では検出できないため、このルールに依存している場合は注意が必要です。

**Unsupported (17件)**
```
17 Unsupported (Won't be implemented: react/jsx-uses-react, react/jsx-uses-vars, react-hooks/static-components, and more)
```
Oxlintが意図的に実装しない方針のルール群です。出力に挙げられている代表例を確認します。

- `react/jsx-uses-react` / `react/jsx-uses-vars`: React 17で導入された[新しいJSX Transform](https://legacy.reactjs.org/blog/2020/09/22/introducing-the-new-jsx-transform.html)により、JSXファイルで`import React from 'react'`が不要になりました。これらのルールは以前の書き方を前提としているため、現在主流の書き方では実質不要なルールです
- `react-hooks/static-components`: Oxlintが実装しない方針として分類されています

### 警告の内容
**1. `special parser detected: eslint-config-next/parser`**

```
* special parser detected: eslint-config-next/parser
```
ESLintのNext.js設定は`eslint-config-next/parser`というカスタムパーサーを利用していますが、OxlintはRustで実装された独自パーサーを持っており、外部のJavaScriptパーサーを組み込む設計になっていません。Oxlint独自パーサーでTypeScript/JSXを解析するため、この警告は無視できます。

**2. `Settings found under a 'files' pattern`**

```
* Settings found under a 'files' pattern — oxlint does not support settings in overrides and they will be skipped:
  * `react`
  * `import/parsers`
  * `import/resolver`
```
`files`パターン内の`settings`フィールドはOxlintがサポートしていないため、これら3つの設定はスキップされます。

- `react`: Reactのバージョン設定
- `import/parsers`: TypeScriptファイル向けのパーサー設定
- `import/resolver`: モジュール解決の設定

これらはOxlintの内部処理で読み込まれているため動作に影響しないことを実際の検証結果（後述）で確認できています。

この差分の原因は、ESLintで設定していた`eslint-config-next`が`react/jsx-uses-react`ルールを有効化しているためです。

- `react/jsx-uses-react`: JSXを使用しているファイルではReact変数を使用済みとみなす

このルールは移行時にスキップされていたため、差分として検出されるのは想定内です。

また、前述の通り新しいJSX Transformにより、現在主流の書き方でこのエラーが出ることはほぼないです。

## 検証結果

`migrate`コマンドを実行するだけで、ESLint/Prettierで検出していた違反をOxlint/Oxfmtでも正しく検出できることが確認できました。

:::message
今回はよく使われるルールにのみフォーカスしており、全プラグインやカスタムルールの検証は行っていません。実際に移行する際は、自プロジェクトでの事前検証を推奨します。
:::

# まとめ

`migrate`コマンドを使うことで、ESLint/PrettierからOxlint/Oxfmtへの移行設定を自動生成できます。

今回の検証では以下が確認できました。

- **Oxlint**: ESLintで検出していた違反はすべて検出できた。1件の差分があったが、古いJSX Transformに依存したルール（`react/jsx-uses-react`）に起因するもので、現代のコードでは実質問題にならない
- **Oxfmt**: Prettierとまったく同じフォーマット結果が得られ、差分はゼロだった

よくある不安である「移行後に既存のルール違反を見逃すのではないか」については、少なくとも主要なルールの範囲では心配する必要はなさそうです。
なので移行を検討している方は`migrate`コマンドで設定を自動生成し、自プロジェクトで正しく動作するか気軽に試してみてください。
